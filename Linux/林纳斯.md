用户程序运行在低特权级（用户态），其页表里没有映射硬件寄存器的物理地址，或者将这些地址设为不可访问，所以一旦尝试访问就会产生段错误。单片机通常没有 MMU，所有代码都运行在特权模式，因此可以直接读写寄存器


但是应用程序不能直接调用驱动程序的代码
那要怎么才能驱动
应用层会先设置一个寄存器，然后故意触发一个异常 SWI(一种汇编指令，相当于中断，**注解(**：在 ARM 旧版本（ARMv4/5/6）中，这条指令叫 **SWI**（Software Interrupt）。  从 ARMv7 开始，它被重命名为 **SVC**（Supervisor Call），含义更清晰。  现在 Linux ARM 内核里用的是 `SVC 0` 或 `SWI 0`，但概念完全相同：软件触发异常，进入内核模式。**)**，触发后CPU会去执行SWI异常处理函数(内核提供)，这就成用户态切换成内核态，内核态里函数就有足够权限来访问硬件，实现了应用程序调用驱动程序，
open read writer,这三个函数都是执行一条SWI指令，那怎么知道是哪个函数触发，这得看R0值，相当于根据R0值判断中断源,然后就根据实际情况调用sys_open,sys_read,sys_writer，对于文件，内核会先判断文件名，如果是普通文件，那就正常操作，如果是驱动文件，那就会找到驱动文件，进行open/read/writer

### 我的 Linux 入门笔记（修正版）

**1. 从单片机到 Linux：为什么不能直接访问硬件？**

单片机里，我的代码想怎么写寄存器就怎么写，直接就能点个灯。  
但是 Linux 下不行，因为有个 **MMU（内存管理单元）**。它会配合 CPU 做权限检查，把用户程序的访问范围限制得死死的，硬件寄存器你根本摸不到。

所以要想在 Linux 里操作硬件，就必须通过**驱动程序**。驱动程序是专门跟硬件打交道的代码，它住在**内核空间**。

**2. 新的问题：应用程序怎么调用驱动程序？**

应用程序跑在普通用户空间，驱动程序在内核空间，它们之间有一堵墙。  
我不能像调自己写的函数那样，直接去 call 驱动里的代码。那墙过不去。

那究竟怎么才能把“帮我点个灯”这个请求，交给驱动呢？

**3. 核心手段：故意触发一次“软中断”**

整个思路是这样的：  
应用程序干不了特权活，但内核可以。那我就让应用程序**主动陷进内核**，让内核替我去找驱动。

具体做法分三步：

- **第一步，传暗号**。  
  C 库函数（比如 `open`）内部，会先把一个**系统调用号**放进一个特定寄存器。在 ARM 架构里，这个寄存器是 **r7**。  
  调用号就像一个工牌号码，告诉内核“我是 open，我来开门”。同时，参数放进 r0、r1、r2 这些寄存器里。

- **第二步，搞事情**。  
  然后它执行一条叫 **SWI**（旧称，新架构叫 SVC）的汇编指令。这条指令的作用，就是人为制造一个异常。

- **第三步，被接管**。  
  CPU 一看到 SWI 指令，立刻停下手头的活，强制跳进内核里预设好的**异常处理函数**。  
  这一刻，**用户态就切到了内核态**。墙上开了一道临时的安检门，你被内核押着走进去了。

**4. 内核里发生的事：凭号办事**

内核的异常处理函数起来后，先看 r7 寄存器里存的调用号是多少。

- 发现是 `__NR_open`，好，我就去执行内核里的 `sys_open` 函数。
- 发现是 `__NR_read`，就去执行 `sys_read`。
- 发现是 `__NR_write`，就去执行 `sys_write`。

**这里要特别注意：** 区分是谁触发的，不是看 r0。r0 只是第一个参数，比如 `open` 的时候 r0 是文件名指针，`read` 的时候 r0 是文件描述符。如果把 r0 当调用号，内核就彻底懵了。

**5. 文件分流：普通文件 vs. 驱动文件**

接下来，内核要处理具体的文件操作。

- 对于 `sys_open`，它不先管文件名长什么样，而是通过 **VFS（虚拟文件系统）** 来判断文件类型。
- 如果是普通文件（比如存磁盘的 txt），那就走常规的文件系统逻辑。
- 如果是**设备文件**（也就是你笔记里说的“驱动文件”，比如 `/dev/led`），内核会发现它关联着一个**主设备号和次设备号**。
- 内核就拿着这个设备号，在自己的驱动注册表里一查，嘿，找到了对应的驱动程序。然后就去调用这个驱动程序里注册好的 `open`、`read`、`write` 函数。

**6. 总结整个链条**

一图以蔽之：  
应用程序调用 `open` → C 库把调用号塞进 r7，参数塞进 r0～r5 → 执行 `SWI` → CPU 切到内核态 → 内核从 r7 拿到调用号 → 调用 `sys_open` → 发现是设备文件 → 根据设备号找到驱动 → 调用驱动的 `open`。  
硬件，终于被点亮了。

整个过程的核心思想，就是利用 CPU 硬件强制提供的**异常切换机制**，让内核短暂地“借出”它的高权限，安全地替用户把事情办了，再迅速收回权限。这就是 Linux 世界里应用层和驱动层对话的根基。
